# Pilot 실험계획서 초안

## Agentic Coding 기반 SDL 물리 장치 구축 벤치마크: Arduino UNO Q 단일 보드, 2모델 사전 검증

문서 버전: v0.2 초안
작성일: 2026-07-20
상태: 미확정 항목 3건 포함, 8절 참조. v0.2에서 시각 피드백 2x2 요인 설계 반영

---

## 1. 본 실험의 위치

본 pilot은 학위 논문 "Agentic Coding으로 Self-Driving Laboratory의 물리 장치 구축을 가속할 수 있는가"의 본실험에 선행하는 사전 검증 실험이다. 본실험은 보드 3종 ESP32-S3-Box, Arduino UNO Q, Raspberry Pi Zero와 모델 3종 Claude, GLM, ChatGPT의 조합을 hardware-in-the-loop, 이하 HIL 방식으로 비교하는 설계이며, pilot은 그중 보드 1종 Arduino UNO Q와 모델 2종 Claude, GLM만으로 측정 체계 전체를 먼저 가동한다.

pilot에서 검증 대상은 모델의 우열이 아니라 실험 인프라 자체다. 구체적으로 다음 다섯 가지 pilot question, 이하 PQ에 답한다.

| ID | Pilot Question | 판단 기준 |
|---|---|---|
| PQ1 | 자동화 하네스가 개입 없이 전체 트라이얼을 완주하는가 | 하네스 원인 중단 0건 |
| PQ2 | 성공 판정 자동화가 사람 판정과 일치하는가 | 전 트라이얼에서 기계 판정과 육안 판정 일치 |
| PQ3 | 트라이얼 간 분산이 어느 정도이며 본실험 반복 수를 몇 회로 정해야 하는가 | 소요 시간의 변동계수 산출 |
| PQ4 | 로컬 모델과 API 모델의 비용을 같은 틀에서 측정할 수 있는가 | 두 비용 산식이 실측 데이터로 계산됨 |
| PQ5 | 태스크 2종의 난이도가 변별력을 갖는가 | 천장 효과와 바닥 효과 부재, 즉 전원 성공이나 전원 실패가 아닐 것 |
| PQ6 | 하드웨어 셋업에 대한 시각 피드백 유무가 구축 성과에 차이를 만드는가 | 조건 간 구축 시간과 성공률의 효과 방향과 크기 산출 |

## 2. 태스크 정의

두 태스크는 SDL 물리 장치 구축의 두 계층을 대리한다. T1은 장치 제어 계층과 상위 오케스트레이션 소프트웨어의 통합을, T2는 센서 기반 폐루프 반응 구축을 대표한다. 난이도는 IoTBench의 3단계 체계에 대응시켜 본실험 task suite와의 연속성을 확보한다.

| 항목 | T1 | T2 |
|---|---|---|
| 명칭 | Home Assistant 기반 RGB actuator 통합 | Vision 기반 폐루프 반응 |
| 목표 | UNO Q에 Home Assistant를 설치하고, 보드 GPIO에 배선된 3핀 RGB LED를 색상 제어 가능한 light 엔터티로 통합한 뒤 빨강 3초, 초록 3초, 파랑 3초, 소등 시퀀스를 시연 | USB 웹캠 영상에서 사람이 감지되면 8x13 LED Matrix에 O자를 표시하고 미감지 시 소등 |
| SDL 대응 계층 | actuator firmware와 lab orchestration 소프트웨어의 통합 | 센서 인지에서 물리 반응까지의 폐루프 |
| 요구 기술 요소 | Docker, Home Assistant onboarding, MQTT 또는 대안 연동 계층, Router Bridge RPC, MCU sketch, PWM | V4L2 카메라, 객체 감지 파이프라인, Router Bridge RPC, MCU sketch, LED Matrix frame |
| IoTBench 난이도 대응 | Level 2 상당에 시스템 통합 추가 | Level 3 상당에 AI 추론 추가 |
| 타임아웃 | 3600초 | 3600초 |

## 3. 실험 설계

### 3.1 요인과 수준

| 구분 | 내용 |
|---|---|
| 독립 변인 1 | 모델 2수준. Claude와 GLM 로컬 모델 |
| 독립 변인 2 | 시각 피드백 2수준. V+는 에이전트에 snap.bat 제공, V-는 미제공 |
| 통제 변인 | 에이전트 프레임워크 Claude Code로 단일화, 프롬프트 본문, 보드, 배선, 네트워크, 초기화 절차, 판정 로직, 카메라 위치와 조명 |
| 종속 변인 | 4절의 측정 지표 전체 |
| 반복 | 조건당 태스크당 3회. 4조건 x 2태스크 x 3회 = 총 24 트라이얼 |
| 순서 | 회차마다 4조건의 실행 순서를 라틴 방진 방식으로 순환해 시간대와 네트워크 편향 상쇄 |

시각 피드백 요인의 조작 정의는 다음과 같다. V+ 조건에서는 프롬프트에 snap.bat의 경로와 용도를 안내하고 에이전트가 호스트 카메라로 보드와 배선, LED 점등 상태를 촬영해 확인할 수 있다. V- 조건에서는 snap.bat을 PATH에서 제거하고 프롬프트에서 해당 안내 문단을 삭제하며, 에이전트는 adb를 통한 텍스트 피드백만으로 하드웨어 상태를 추론해야 한다. 하네스의 판정용 촬영은 두 조건 모두에서 동일하게 수행되므로 조건 간 차이는 에이전트의 지각 능력에만 국한된다.

이 요인이 검증하는 가설은 물리 세계에 대한 시각적 접지, visual grounding이 embedded 개발 agent의 오류 발견과 수정 주기를 단축한다는 것이다. SDL 맥락에서 이는 구축 현장에 카메라 한 대를 두는 저비용 개입이 구축 효율을 바꾸는지에 대한 실용적 질문이기도 하다. 다만 조건당 3회의 pilot 규모에서는 통계적 검정이 아니라 효과의 방향과 크기 추정, 그리고 상호작용 존재 가능성의 관찰까지만 수행하고, 유의성 검정은 본실험에서 산정된 표본 수로 수행함을 명시한다.

프레임워크 단일화의 의도는 다음과 같다. 두 모델 모두 Claude Code를 하네스로 사용한다. GLM 로컬 서빙은 OpenAI 호환 엔드포인트이므로 Anthropic Messages 형식을 OpenAI Chat Completions 형식으로 변환하는 프록시, 예를 들어 LiteLLM을 중간에 두고 Claude Code의 ANTHROPIC_BASE_URL을 프록시 주소로 지정한다. 이로써 비교 대상이 제품 대 제품이 아니라 모델 대 모델로 정의되며, 도구 호출 루프와 컨텍스트 관리 등 프레임워크 성능이 통제된다. 변환 프록시는 GLM 파이프라인에만 존재하는 비대칭 요소이므로, preflight에서 tool calling 스키마와 이미지 입력의 변환 충실도를 검증하고 프록시 지연 시간을 별도 기록해 구축 시간 해석에 반영한다. 이 구성은 논문 본문에 한계와 함께 명시한다.

### 3.2 실험 환경

| 구성 요소 | 사양 |
|---|---|
| 대상 보드 | Arduino UNO Q, Qualcomm QRB2210 4코어 arm64, Debian Trixie, RAM과 eMMC 용량은 실물 기준 기재 |
| 호스트 | Windows PC, Claude Code 및 GLM 로컬 서빙 |
| 보드 제어 경로 | adb over Wi-Fi, adb connect 보드IP:5555 |
| T1 하드웨어 | 공통 캐소드 여부 확정 필요. RGB LED를 D9, D10, D11에 220Ω 저항 경유 배선, 공통 핀 GND. 핀은 모두 PWM 지원, 로직 레벨 3.3V |
| T2 하드웨어 | PD passthrough 지원 전원 공급형 USB-C 허브, UVC 웹캠 |
| 검증용 카메라 | 호스트 PC 장착, LED Matrix와 RGB LED가 한 프레임에 들어오도록 고정. ffmpeg dshow 캡처 |

### 3.3 사전 준비 목록

사람이 수행하며, 측정 시간에 포함되지 않는다.

1. 보드 Wi-Fi 연결과 adb over Wi-Fi 활성화, 재부팅 후 재연결 절차 확인
2. passwordless sudo 설정
3. T1 배선과 T2 허브, 웹캠 장착 후 lsusb와 /dev/video 존재 확인
4. 호스트 카메라 고정 설치, LED 영역 좌표 캘리브레이션, snap.bat 동작 확인
5. GLM 로컬 서빙 기동, 변환 프록시 구성, 프록시 경유 tool calling과 이미지 입력 처리 여부 확인, 8절 미확정 항목
6. 프록시 왕복 지연 시간 측정과 기록
7. 하네스 preflight 통과 확인

## 4. 측정 지표

### 4.1 지표 정의

| 분류 | 지표 | 정의 | 수집 방법 |
|---|---|---|---|
| 1차 | 성공 여부 | 5절 판정 프로토콜의 전 단계 충족 | 하네스 자동 판정 |
| 1차 | 구축 시간 | 에이전트 프로세스 기동부터 성공 판정 시점까지의 wall-clock 초 | 하네스 타임스탬프 |
| 1차 | 비용 | 4.2절 산식 | 토큰 로그와 전력 실측 |
| 2차 | adb 호출 수 | 래퍼가 기록한 보드 명령 총수 | adb.bat 래퍼 로그 |
| 2차 | 시각 검증 활용 | V+ 조건에서 snap.bat 호출 횟수, 촬영 직후 행동 변화 여부, 촬영으로 발견한 오류 수 | 래퍼 로그와 세션 로그 사후 코딩 |
| 2차 | 오류 복구 횟수 | 실패한 명령 후 대안 시도로 이어진 횟수 | 세션 로그 사후 코딩 |
| 2차 | 감지 반응 지연 | T2에서 사람 등장 시점부터 matrix_draw_o 로그까지의 초 | 하네스 이벤트 대조 |
| 기록 | 보드 리소스 | 15초 간격 메모리, load average, 디스크 | 모니터 스레드 |

### 4.2 비용 산식

로컬 모델과 API 모델의 비용을 단일 축으로 비교하기 위해 두 산식을 병기하고, 논문에는 두 값을 모두 보고한다.

| 산식 | Claude | GLM 로컬 |
|---|---|---|
| 산식 A 요금 기준 | 실제 API 과금액. 입력과 출력 토큰별 단가 곱 | 동일 토큰 수를 공개 API 단가에 대입한 가상 과금액 |
| 산식 B 자원 기준 | 해당 없음, N/A 처리 | 트라이얼 중 GPU 전력 실측 적산 와트시와 점유 시간 |

성공당 비용 cost per success는 트라이얼 비용 합을 성공 수로 나누어 별도 보고한다. 실패 트라이얼의 비용이 분자에 포함되는 정의임을 명시한다.

### 4.3 표본 수 산정 근거 마련

pilot의 구축 시간 표준편차 s를 이용해 본실험 반복 수 n을 산정한다. 두 모델 평균 차이의 최소 검출 효과 크기를 pilot 관측 평균의 20퍼센트로 두고, 유의수준 0.05와 검정력 0.8 기준 표본 수 공식을 적용한 결과를 본실험 계획서에 기재한다. pilot의 조건당 3회는 이 산정을 위한 최소치다.

### 4.4 시각 피드백 요인의 분석 계획

2x2 설계에서 관심 효과는 세 가지다. 첫째, 시각 피드백의 주효과, 즉 V+ 평균과 V- 평균의 구축 시간과 성공률 차이. 둘째, 모델의 주효과. 셋째, 두 요인의 상호작용, 즉 시각 피드백의 이득이 모델에 따라 다른지 여부다. 상호작용이 관찰되면 특정 모델이 시각 정보를 더 잘 활용한다는 해석이 가능하며 이는 본실험의 독립적 기여 지점이 된다. pilot 규모에서는 셀당 3회로 검정력이 부족하므로 효과 크기와 방향만 산출하고, 시각 검증 활용 지표의 세션 로그 분석으로 정량 결과를 보완하는 혼합 방법을 취한다. 촬영이 실제로 오류 발견으로 이어진 에피소드를 코딩해 시간 단축의 기전을 질적으로 기술한다.

## 5. 판정 프로토콜

판정은 에이전트의 자기 보고와 무관하게 하네스가 독립 수행한다. 에이전트의 snap.bat 자가 촬영은 디버깅 도구로 취급하며 판정 근거에서 배제한다.

### 5.1 T1 판정

| 단계 | 기준 | 확인 방법 |
|---|---|---|
| 1 | 포트 8123 HTTP 응답 | 보드 내부 curl |
| 2 | RGB 색상 지원 light 엔터티 존재 | HA REST API /api/states |
| 3 | 데모 시퀀스 이력 | 엔터티 rgb_color 속성이 빨강, 초록, 파랑, 소등 순으로 전환된 상태 이력 |
| 4 | 물리 점등 일치 | 각 색상 구간에 호스트 카메라로 촬영한 프레임에서 LED 영역 지배 hue가 해당 색과 일치 |

### 5.2 T2 판정

| 단계 | 기준 | 확인 방법 |
|---|---|---|
| 1 | 웹캠 파이프라인 가동 | 지정 로그 파일에 person_detected 이벤트 기록 |
| 2 | RPC 전달 | matrix_draw_o 기록이 감지 이벤트와 시간순 정합 |
| 3 | 물리 점등 | 사람 등장 연출 시점에 호스트 카메라 프레임에서 O자 점등 확인 |
| 4 | 소등 동작 | 사람 퇴장 후 matrix 소등 확인 |

T2의 사람 등장 연출은 회당 1회, 동일 인물이 동일 거리와 조명에서 수행한다. 연출 시각은 하네스에 수동 마킹한다.

### 5.3 실패 유형 분류

실패 트라이얼은 다음 코드로 분류해 기록한다. FT1 환경 인식 실패, FT2 설치 실패, FT3 연동 계층 실패, FT4 sketch 빌드 또는 배포 실패, FT5 판정 기준 미달, FT6 타임아웃, FT7 네트워크 상실, FT8 하네스 결함. FT8은 모델 성능이 아닌 인프라 문제로 집계에서 제외하고 트라이얼을 재실행한다.

## 6. 프롬프트 표준화

프롬프트는 태스크별로 V+와 V- 두 변형을 두되, 두 변형의 차이는 4번 도구 안내 문단의 snap.bat 항목 존재 여부 하나로만 국한한다. 나머지 본문은 문자 단위로 동일하며, 같은 조건 안에서는 두 모델이 문자 단위 동일한 프롬프트를 받는다. 프롬프트 구성 요소는 다음과 같으며 전문은 부록으로 확정한다.

1. 환경 고지. 보드 종류, adb over Wi-Fi 연결 상태, passwordless sudo, 보드가 이미 네트워크에 연결됨
2. 하드웨어 사실. T1은 LED 타입과 핀 배정, 저항, 로직 레벨. T2는 웹캠 장치 존재와 LED Matrix 8x13
3. 완료 조건. 판정 프로토콜과 동일한 문구
4. 도구 안내. 지정 로그 파일 경로. V+ 조건에 한해 snap.bat 경로와 용도 추가
5. 금지 사항. 보드 재부팅 금지, 네트워크 설정 변경 금지, 사용자 질문 금지
6. 구현 경로는 지정하지 않음. 연동 계층과 감지 파이프라인 선택은 모델의 탐색 능력으로 측정

## 7. 실행 절차

트라이얼 단위 절차는 다음과 같다.

1. preflight. adb 연결, 보드 사양 스냅샷, 8123 포트 무응답 확인, 호스트 카메라 촬영 확인
2. 초기화. Docker 엔진과 이미지, HA 데이터, MQTT 브로커, systemd 유닛, ArduinoApps 신규 앱 제거. NetworkManager 설정은 제외 목록으로 고정
3. 에이전트 기동과 병렬 모니터링. 리소스 샘플링, adb와 snap 래퍼 로그
4. 판정 폴링. 성공, 타임아웃, 에이전트 종료 후 유예 120초 중 먼저 도래하는 조건으로 종료
5. 사후 수집. 세션 로그, 토큰 사용량, GPU 전력 적산, 증거 사진 보관
6. 육안 판정 기록. PQ2 검증을 위해 기계 판정과 별도로 사람이 성공 여부를 기록

일정은 1일차 preflight와 하네스 리허설, 2일차와 3일차 T1 12 트라이얼, 4일차와 5일차 T2 12 트라이얼, 6일차 분석과 본실험 계획 갱신으로 총 6일을 상정한다. 하루 6 트라이얼은 회당 최대 1시간의 타임아웃과 초기화 시간을 감안한 값이다.

## 8. 미확정 항목

| 번호 | 항목 | 선택지 | 결정 기한 |
|---|---|---|---|
| 1 | 웹 검색 허용 | 양쪽 허용 또는 양쪽 차단. UNO Q가 2025년 10월 출시라 학습 데이터 부재 가능성이 높아 허용 시 문서 탐색 능력까지 측정, 차단 시 순수 사전 지식 측정 | preflight 전 |

| 3 | RGB LED 타입 | 공통 캐소드 또는 공통 애노드. 프롬프트 문구와 배선에 직결 | 배선 전 |
